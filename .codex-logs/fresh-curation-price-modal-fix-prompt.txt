## 버그

`updatePriceCalcQuantity()`가 `priceCalcQuantity`의 `input` 이벤트(키 입력마다)에서 실행되는데, 이 함수는 매번
현재 값을 `priceCalcStep`의 배수로 즉시 반올림해서 `priceCalcQuantity.value`를 덮어씁니다.

- 낱개 상품(`priceCalcStep = 1`)은 반올림이 항등 변환이라 문제가 없습니다.
- 무게 상품(`priceCalcStep = 100`)은 문제가 됩니다. 예를 들어 사용자가 "300"을 입력하려고 "3"만 타이핑해도
  `Math.round(3/100)=0 → Math.max(1,0)=1 → 필드 값이 즉시 "100"으로 강제 변경`되어, 키보드로 여러 자리 숫자를
  이어서 입력하는 것이 사실상 불가능합니다(스테퍼 +/- 버튼으로만 100g씩 조작 가능한 상태가 됨).

## 원하는 동작

- 사용자가 무게 입력창에 직접 타이핑하는 동안(`input` 이벤트)에는 **필드 값을 강제로 스냅/덮어쓰지 않고**,
  현재 입력된 원시 값을 기준으로 총액 미리보기(원가/도매가/판매가의 "총액" 칸)만 실시간으로 갱신합니다.
  (예: "3"을 입력한 시점이면 `factor = 3/100`으로 잠정 계산해서 미리보기에 반영해도 되고, 값이 정수배가
  아니면 그 시점의 원시 값 그대로 계산해도 됩니다 — 요점은 입력 필드 자체를 강제로 되돌리지 않는 것입니다)
- 값을 100 단위로 스냅/정규화하는 것은 아래 시점에만 적용하세요:
  - `+`/`-` 스테퍼 버튼 클릭 시(기존처럼 정확히 100 단위로 증감)
  - 입력창에서 포커스가 벗어날 때(`change` 이벤트, 즉 타이핑을 마치고 다른 곳을 클릭했을 때)
- 개수(낱개, step=1) 쪽은 현재 동작 그대로 두어도 됩니다(반올림이 항등 변환이라 원래 문제 없음). 다만 하나의
  공용 함수를 쓰고 있으니, 위 수정이 낱개 쪽 동작을 바꾸지 않는지 확인하세요.
- `priceCalcFactor`가 이 과정에서 0이나 음수, NaN이 되는 경우가 없도록 하세요(예: 필드가 비어있는 도중에는
  최소 1e-9 같은 극단값 대신, 총액 계산을 건너뛰거나 이전 값을 유지하는 방식으로 방어하세요).
